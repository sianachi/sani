Sani is a small broker that sits between AI coding agents and the credentials they need. The agent never holds a token. It requests one action, a person approves that exact request in a browser, and the agent gets back a screened result.

$ npx github:sianachi/sani

Needs Node.js 24.13 or newer. Nothing to clone or configure first.

How it works

The credential stays on the Sani server. The agent only ever holds a Sani key, which can ask for an action and read the result of its own request.

Nothing is sent until you approve. A pending request expires after 15 minutes, and one approval sends that call once.

Two ways to use it

Together or separately. Both go through the same approval page.

MCP tool calls

Connect an authenticated MCP server such as GitHub or Linear. The agent requests one of the tools you enabled, and Sani makes the call with the stored token or OAuth sign-in.

The connection form has read-only starting points for Linear and GitHub pull requests.

Shell commands

Store a secret such as GH_TOKEN. The agent requests a command and Sani runs it in a throwaway Docker container with only the secrets that command named.

$ gh pr list --repo acme/site

Works with any client that speaks MCP over HTTP, including Claude Code and Codex.

Try the demo

Demo mode adds a built-in connection named demo. It stores no credential and cannot reach the network or other systems, so you can see the approval flow before you connect a real platform.

$ SANI_DEMO=1 npx github:sianachi/sani

Demo mode is off unless you set it. Real connections are unchanged.

  1. 1Sani prints a sign-in address and, on the first run, your operator password.
  2. 2Sign in at http://127.0.0.1:8765 and create an agent token. Sani shows it once.
  3. 3Request lookup_ticket on the demo connection with id 1001. Nothing runs until you approve.
  4. 4Open the approval link, approve, and read the screened result: a sample ticket titled “Welcome to Sani”.

The security boundary

What Sani does to keep a credential away from the agent, and where that protection stops.

Area What Sani does Where it stops
Storage Bearer tokens and OAuth tokens are stored encrypted on the server and are never given to the agent. Request arguments and results are stored as plain JSON. Protect the database file like the data it holds.
Screening Stored credentials are withheld from tool definitions, arguments and results, including URL-encoded and base64 forms. It is not a secret scanner. It looks for the credentials Sani stores, not for secrets in general.
Outbound calls Platform calls go over public HTTPS only. Sani refuses redirects and private, loopback and link-local addresses. The sandbox does not contain the secret. An approved command can send its secrets anywhere the container can reach.
Approval One approval sends one call. Decline, expiry and an unknown outcome are final. Changing a credential or tool invalidates waiting requests. There is one operator and no sign-in throttling. Put a rate-limiting reverse proxy with HTTPS in front of a Sani that others can reach.

Status

Sani is a release candidate, 1.0.0-rc.5. The interface may still change before 1.0, and it has not had an independent security audit. Start with read-only tools and restricted test credentials.

  • Tested on macOS and Linux. Windows has not been tried.
  • Not on npm yet. Use npx github:sianachi/sani.
  • No sandbox commands when Sani itself runs in Docker.
  • First-run setup keeps the encryption key beside the database. Set your own key before storing credentials that matter.
